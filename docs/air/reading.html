Privacy policy

Privacy should be easy to read. Where your work lives, when a connection is needed, and the choices that stay in your hands.

A shared reading pattern. Each product keeps its own verified policy.

This is a design study, not a replacement privacy policy. Product-specific wording and revision dates must stay accurate when this layout is adopted.

Your files

A file can be processed on your device without being sent to an application server. A useful privacy page explains that boundary in plain words and identifies any feature that behaves differently.

Documents, images and résumé text are the work itself. Describe where they are processed separately from the application code, fonts or optional tools that a browser may download.

Work you choose
The original file and the changes you make to it.
Application resources
The code and supporting assets needed to run a feature.
Files you export
A separate result you choose to save on your device.

Saved work

Local processing and local storage are different promises. A draft kept in browser storage may survive a reload; an unsaved change held only in memory may not.

A product policy should identify which drafts, settings and cached resources it stores, how long they remain, and how to remove them. It should also explain what can be lost when site data is cleared.

Keep the recovery action close to the problem. Tell someone what is safe before asking them to reload or leave their work.

The saved-work recovery study shows an editable note, a failed-save message and an independent text backup.

Connections

Some features need supporting downloads. A model, dictionary or codec can be fetched to the device while the work itself stays local. Name the provider and the purpose where the product actually makes that request.

  • Explain which action starts a download, its size and any device requirements.
  • Distinguish a first download from reuse of a cached resource.
  • Provide useful cancellation, failure and retry states.
  • Describe what the contacted service can receive without claiming that every network request contains a document.

A native download manager also contacts the destinations chosen by its user. The family layout must accommodate those details; it must never replace them with an inaccurate “no network” claim.

Your choices

Describe the real controls available in the product. Downloading a copy, removing a saved draft and clearing a model cache are different actions with different consequences.

  1. Save a copy of any work you want to keep.
  2. Check which local data a removal action affects.
  3. Use the product or browser control that matches that choice.

Destructive actions need a clear consequence and a safe way back when one exists. Do not promise recovery for a permanent deletion, or suggest that removing an application also removes every file it created.

Questions

Use a product’s published contact or reporting route for questions about its policy. Never ask someone to put private document content, credentials or personal information into a public issue.

Maintained references should be readable, descriptive links rather than raw addresses. Long identifiers still wrap when they are needed, for example browser-local-draft-recovery-reference-with-a-deliberately-long-identifier.
